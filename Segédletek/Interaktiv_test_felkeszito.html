1 — Teszttípusok példákkal
⚡Unit Teszt (Egységteszt)Unit
Mi ez?
Az alkalmazás legkisebb önálló egységét (metódus, függvény) teszteli izoláltan, minden külső függőség (DB, API, fájl) nélkül. Gyors, determinisztikus, a fejlesztő írja.
Mit tesztelünk?
Egyetlen metódus visszatérési értékét, kivételdobását, mellékhatásait — adott bemenetre adott kimenetet várunk (AAA-minta: Arrange → Act → Assert).
C# · xUnit · Kalkulátor unit teszt
// Osztály amit tesztelünk
public class Kalkulátor {
    public int Összeadás(int a, int b) => a + b;
    public double Osztás(double a, double b) {
        if (b == 0) throw new DivideByZeroException();
        return a / b;
    }
}

// xUnit tesztosztály
public class KalkulátorTesztek {
    private readonly Kalkulátor _kalc = new();

    [Fact]
    public void Összeadás_KétPositívSzám_HelyesEredmény() {
        // Arrange
        int a = 3, b = 7;
        // Act
        int eredmény = _kalc.Összeadás(a, b);
        // Assert
        Assert.Equal(10, eredmény);
    }

    [Fact]
    public void Osztás_NullOsztóval_KivételenDobjon() {
        Assert.Throws<DivideByZeroException>(() => _kalc.Osztás(10, 0));
    }
}
🔗Integrációs TesztIntegráció
Mi ez?
Több modul/réteg együttes működését teszteli. Pl. Controller → Service → Repository → DB lánc valódi adatbázissal.
Célja
Megtalálni azokat a hibákat, amelyek az egységek határán keletkeznek (interfész-eltérések, adat-mapping hibák).
Példa (C#)
Egy UserService.CreateUser() hívás valóban ment-e a tesztadatbázisba? Az API végpont visszaad-e 201 Created státuszt?
Eszközök
xUnit + In-memory DB, Testcontainers (Docker DB), WebApplicationFactory (ASP.NET Core)
🌐End-to-End (E2E) TesztE2E
Mi ez?
A teljes alkalmazást teszteli valós böngészőn vagy UI-on keresztül, úgy ahogy a felhasználó használja.
Célja
Üzleti folyamatok végponttól végpontig való ellenőrzése: regisztráció → bejelentkezés → vásárlás → visszaigazolás.
Példa
Selenium: nyissa meg a böngészőt, töltse ki az űrlapot, kattintson, ellenőrizze az eredményt. Playwright, Cypress hasonlóan.
Hátrány
Lassú, törékeny (UI változásokra érzékeny), nehéz karbantartani. Ezért a piramison a tetején van.
👁️Manuális TesztManuális
Mi ez?
Emberi tesztelő hajtja végre kézzel, tesztterv alapján. Nem automatizált.
Fajtái
Exploratory: nem szkriptelt, a tesztelő kreativitása alapján. Scripted: lépésről lépésre tesztterv szerint.
Mikor?
UX vizsgálathoz, felhasználói elfogadási tesztelésnél (UAT), új funkciók első körös ellenőrzésekor.
🔄Regressziós TesztRegresszió
Mi ez?
Annak ellenőrzése, hogy egy változtatás (bugfix, új funkció) nem törte-e el a korábban működő részeket.
Hogyan?
Általában automatizált: a teljes (vagy részleges) tesztkészlet újrafuttatása minden kódmódosítás után (CI/CD pipeline).
Példa
Fizetési modul javítása után az összes checkout-tesztet újrafuttatjuk, hogy biztosan semmi nem romlott el.
📈Teljesítmény- és TerheléstesztPerf
Load Test
Normál várható terhelésen mér válaszidőt és erőforrás-használatot (pl. 100 egyidejű felhasználó).
Stress Test
A rendszer töréspontját keresi — meddig bírja, mielőtt összeomlik vagy lelassul.
Spike Test
Hirtelen forgalomcsúcs szimulálása (pl. akció indulása webáruházban).
Eszközök
k6, JMeter, Locust, Gatling
🔒Egyéb teszttípusokSpec
🔥 Smoke Test
Gyors „él-e a rendszer?" ellenőrzés telepítés után. Ha megbukik, nincs értelme tovább tesztelni.
✅ UAT (User Acceptance)
Megrendelő / végfelhasználó ellenőrzi, hogy a szoftver teljesíti-e az üzleti követelményeket.
🔐 Biztonsági teszt
SQL injection, XSS, hitelesítési hibák keresése. Eszközök: OWASP ZAP, Burp Suite.
♿ Accessibility teszt
WCAG szabványok teljesítésének ellenőrzése (kontrasztarány, screen reader kompatibilitás).
2 — Tesztpiramis (Mike Cohn)
△Testing Pyramid
E2E / UI
Integrációs
Unit tesztek
Lentről felfelé haladva: sok unit (gyors, olcsó, izolált) → kevesebb integrációs → még kevesebb E2E (lassú, drága, törékeny). A piramis alján kell a legtöbb tesztet tartani.
🏆Tesztelési szintek (ISTQB)
L1
Komponenstesztelés (Unit)
Egyedi modulok izolált tesztelése. Fejlesztők végzik. Mock objektumok használata.
L2
Integrációs tesztelés
Modulok együttműködésének ellenőrzése. Top-down, bottom-up vagy big-bang stratégia.
L3
Rendszertesztelés
A teljes rendszer funkcionális és nem-funkcionális követelményeknek való megfelelése.
L4
Elfogadási tesztelés (UAT)
Megrendelő és végfelhasználó teszteli. Alfa (fejlesztőnél), béta (ügyféleknél) teszt.
3 — Teszttervezési módszerek
⬛Feketedoboz-tesztelésBlack-box
A belső implementáció ismerete nélkül tesztelünk — csak a bemenet/kimenet alapján. Specifikáció-alapú tesztelés.
▸
Ekvivalencia-partícionálás
A bemenetek érvényes és érvénytelen osztályokra bontása. Osztályonként elég 1 teszteset. Pl. kor mező: [<0], [0–17], [18–120], [>120]
▸
Határérték-analízis (BVA)
Az osztályok határain tesztelünk, mert ott a legtöbb hiba. Pl. ha érvényes tartomány [1–100]: tesztek: 0, 1, 100, 101
▸
Döntési tábla
Feltételek és cselekvések kombinációit táblázatban kezeljük. Összetett üzleti szabályoknál hasznos.
▸
Állapotátmenet-tesztelés
Állapotgép-diagramok alapján ellenőrzi, hogy az összes átmenet helyes-e (pl. rendelés állapotai).
⬜Fehérdoboz-tesztelésWhite-box
A forráskód ismeretében tesztelünk — belső logika, elágazások, útvonalak lefedettségét ellenőrizzük.
▸
Utasításlefedettség (Statement)
Minden kódsor lefutott-e legalább egyszer? Leggyengébb metrika, de minimális alap.
▸
Ágaklefedettség (Branch)
Minden if/else ág (igaz ÉS hamis út) lefutott-e? Pl. if (x>0) mindkét ága tesztelt.
▸
Feltétellefedettség (Condition)
Összetett feltételek minden elemi részfeltételének igaz/hamis értéke tesztelt (MC/DC kritérium).
▸
Útvonallefedettség (Path)
Minden lehetséges végrehajtási útvonal tesztelt. Teljes lefedettség garantált, de exponenciálisan nő.
🩶Szürkedoboz-tesztelésGrey-box
A fekete- és fehérdoboz kombinációja: részleges belső ismeret alapján tesztelünk (pl. API struktúra, DB séma ismert, de a kód nem).
▸
Mikor alkalmazzuk?
Integrációs és rendszerteszteléskor, amikor a tesztelő ismeri az architektúrát, de nem a részletes kódot.
▸
Statikus tesztelés
Kód futtatása nélkül: kódátvizsgálás (review), walkthrough, inspection, statikus analízis (linter, SonarQube). Korán megtalálja a hibákat.
▸
Dinamikus tesztelés
A kódot ténylegesen futtatjuk valódi vagy tesztadatokkal — ez a legtöbb hagyományos teszt.
4 — Tesztelési fázisok (V-modell)
📅Tesztelési folyamat fázisai (ISTQB)
1. Teszttervezés
Teszt stratégia, célok, erőforrások, kockázatok meghatározása. Tesztterv dokumentum elkészítése.
2. Tesztelemzés
Mit tesztelünk? Tesztfeltételek azonosítása a specifikáció alapján (követelmények elemzése).
3. Teszt tervezése
Hogyan tesztelünk? Tesztesetek, tesztadatok és tesztkörnyezet tervezése.
4. Tesztkörnyezet kialakítása
Tesztelési infrastruktúra felállítása: szerver, DB, teszt-adatok betöltése, CI-pipeline.
5. Tesztek végrehajtása
Tesztesetek futtatása, hibák naplózása, hibajelentések (bug report) elkészítése.
6. Teszt lezárása
Kilépési feltételek ellenőrzése, teszt összefoglaló, tanulságok dokumentálása (retrospektív).

5 — ISTQB alapelvek, személyek, fejlesztési módszertanok
📜7 Tesztelési alapelv (ISTQB)
1
A tesztelés hibákat mutat ki — nem bizonyít helyes működést
Teszteléssel hibák jelenlétét bizonyíthatjuk, de teljes hiányukat soha nem.
2
Kimerítő tesztelés lehetetlen
Minden input kombinációt nem lehet letesztelni — kockázatelemzés alapján priorizálunk.
3
Korai tesztelés (Shift-left)
Minél korábban kezdjük el a tesztelést, annál olcsóbb a hibák javítása.
4
Hibacsoportosulás (Defect Clustering)
A hibák 80%-a a kód 20%-ában koncentrálódik (Pareto-elv). A kockázatos modulokra fókuszálj.
5
A rovarirtó paradoxon (Pesticide Paradox)
Ha ugyanazokat a teszteket ismételgetjük, nem találunk új hibákat — rendszeresen frissíteni kell a teszteseteket.
6
A tesztelés kontextusfüggő
Más módszert igényel egy webáruház vs. orvosi beágyazott szoftver tesztelése.
7
A hibamentesség téveszméje
Ha a szoftver a rossz követelményeket teljesíti hibátlanul, attól még használhatatlan. A helyes spec is elengedhetetlen.

6 — TDD ciklus C# példán & Mock objektumok
🔴TDD: Red → Green → Refactor — Banki átutalás példa
TDD-ben ELŐBB írjuk a tesztet (ami elbukik — RED), majd a minimális kódot ami átmegy (GREEN), végül refaktorálunk (REFACTOR).
C# · xUnit + Moq — TDD + Mock példa
// ──── STEP 1: RED — Előbb megírjuk a tesztet (még nem létezik a kód) ────
[Fact]
public void Utalás_ElegendőFedezet_SikeresEsNaplózvaMeg() {
    // Arrange — Mock objektum: nem kell valódi adatbázis
    var mockNapló = new Mock<INaplózó>();
    var számla = new BankSzámla(1000m, mockNapló.Object);

    // Act
    számla.Utal(300m, "Cél-123");

    // Assert — egyenleg csökkent
    Assert.Equal(700m, számla.Egyenleg);
    // Assert — a mock naplózó pontosan egyszer lett meghívva
    mockNapló.Verify(n => n.Naplóz(It.IsAny<string>()), Times.Once());
}

[Fact]
public void Utalás_NemElegendőFedezet_KivételenDobjon() {
    var számla = new BankSzámla(100m, new Mock<INaplózó>().Object);
    Assert.Throws<InvalidOperationException>(() => számla.Utal(500m, "Cél-123"));
}

// ──── STEP 2: GREEN — Minimális implementáció ────
public interface INaplózó { void Naplóz(string üzenet); }

public class BankSzámla {
    private readonly INaplózó _napló;
    public decimal Egyenleg { get; private set; }

    public BankSzámla(decimal kezdőEgyenleg, INaplózó napló) {
        Egyenleg = kezdőEgyenleg; _napló = napló;
    }
    public void Utal(decimal összeg, string célSzámla) {
        if (összeg > Egyenleg) throw new InvalidOperationException("Nincs fedezet");
        Egyenleg -= összeg;
        _napló.Naplóz($"Utalás: {összeg} → {célSzámla}");
    }
}

2 — SOLID elvek (Robert C. Martin)
SSingle Responsibility Principle
Egy osztálynak csak egy oka legyen a változásra — csak egy felelőssége legyen.
C# — SRP megsértése vs. betartása
// ❌ ROSSZ — egy osztály túl sokat csinál
class Felhasználó {
    public void Mentés() { /* DB logika */ }
    public void EmailKüldés() { /* SMTP logika */ }
    public string HtmlMegjelenítés() { /* UI logika */ }
}

// ✅ JÓ — szétválasztva
class Felhasználó { /* csak adat */ }
class FelhasználóRepository { public void Mentés(Felhasználó f) {} }
class EmailSzolgáltatás { public void Küld(Felhasználó f) {} }
OOpen/Closed Principle
Az osztályok legyenek nyitottak a bővítésre, de zártak a módosításra. Új funkció = új osztály, ne meglévő módosítása.
C# — OCP öröklődéssel
// Alap absztrakt osztály — lezárt
abstract class Kedvezmény {
    public abstract decimal Számol(decimal ár);
}
// Bővítés módosítás nélkül — új osztállyal
class DiákKedvezmény : Kedvezmény {
    public override decimal Számol(decimal ár) => ár * 0.8m;
}
class NyugdíjasKedvezmény : Kedvezmény {
    public override decimal Számol(decimal ár) => ár * 0.7m;
}
LLiskov Substitution Principle
Egy leszármazott osztály bármikor helyettesíthető az ős helyén, a program helyes működése nélkül.
C# — LSP megsértése (klasszikus példa)
// ❌ LSP sérül — Négyzet nem igazi Téglalap
class Téglalap {
    public virtual int Szélesség { get; set; }
    public virtual int Magasság { get; set; }
}
class Négyzet : Téglalap {
    // Kénytelen mindkettőt egyszerre állítani → megszegi az LSP-t
    public override int Szélesség { set { base.Szélesség = base.Magasság = value; } get => base.Szélesség; }
}
// Megoldás: közös IAlak interfész, nem öröklés
IInterface Segregation Principle
Ne kényszeríts osztályokat olyan metódusok implementálására, amelyeket nem használnak. Sok kis interfész > egy nagy.
C# — ISP szétbontással
// ❌ ROSSZ — Nyomtató nem tud faxolni
interface IGép { void Nyomtat(); void Faxol(); void Szkennol(); }

// ✅ JÓ — szétválasztott interfészek
interface INyomtató   { void Nyomtat(); }
interface IFax        { void Faxol(); }
interface IScanner    { void Szkennol(); }
class EgyszerűNyomtató : INyomtató { /* csak nyomtat */ }
class MultiFunkciós : INyomtató, IFax, IScanner { /* mindent tud */ }
DDependency Inversion Principle
Magas szintű modulok ne függjenek alacsony szintű moduloktól — mindkettő absztrakcióktól függjön. Dependency Injection alapja.
C# — DIP & Constructor Injection
// ❌ ROSSZ — Service maga hozza létre függőségét
class RendelésService {
    private readonly MySQLAdatbázis _db = new MySQLAdatbázis(); // szoros kapcsolat!
}

// ✅ JÓ — interfészen keresztül, kívülről injektálva
interface IAdatbázis { void Ment(Rendelés r); }
class RendelésService {
    private readonly IAdatbázis _db;
    public RendelésService(IAdatbázis db) { _db = db; } // DI konstruktoron át
}

// Élesben:  new RendelésService(new MySQLAdatbázis())
3 — Egyéb alapelvek & kódszagok
📐Egyéb tervezési elvek
DRY
Don't Repeat Yourself
Minden tudáselemet egyszer, egy helyen kell tárolni. Az ismétlés divergenciához vezet: egyiket javítják, a másikat elfelejtik.
KISS
Keep It Simple, Stupid
A legegyszerűbb megoldást válaszd. Ne tervezz jövőbeli, bizonytalan igényekre — az over-engineering drága.
YAGNI
You Aren't Gonna Need It
Ne implementálj olyasmit, ami „majd egyszer hasznos lesz". Csak a jelen követelményt oldd meg.
LoD
Law of Demeter (Least Knowledge)
Csak a közvetlen szomszédoddal beszélj. a.GetB().GetC().Csinál() lánc veszélyes — szoros csatolás.
SoC
Separation of Concerns
Különítsd el az alkalmazás különböző területeit (UI, üzleti logika, adatelérés). MVC, Clean Architecture erre épül.
🦨Kódszagok (Code Smells)
💀
Long Method / Long Class
Ha egy metódus több mint 20–30 sor, vagy egy osztálynak 200+ sora van — refaktorálni kell.
💀
God Object / God Class
Egy osztály „mindent tud és mindent csinál". SRP súlyos megsértése. Jellemzően több száz metódusa van.
💀
Magic Numbers / Strings
if (x == 7) — mi a 7? Használj elnevezett konstanst: const int MaxPróbálkozás = 7;
💀
Duplicate Code
Ugyanaz a kódrészlet több helyen — DRY-sértés. Refaktorálás: extract method, extract class.
💀
Long Parameter List
4+ paraméter metódusonként → Parameter Object minta. Pl. CímAdatok cím 4 string helyett.
💀
Dead Code
Kommentelt kód, sosem hívott metódusok — töröld ki. A verziókezelő (Git) visszahozza ha kell.
🔧Refaktorálás
A kód belső szerkezetének javítása a külső viselkedés megváltoztatása nélkül. Martin Fowler: „Refactoring" (1999).
▸
Extract Method
Kódrészlet kiemelése saját metódussá. Legelterjedtebb refaktorálás.
▸
Rename (változó / metódus / osztály)
Az elnevezés megváltoztatása, hogy jobban tükrözze a szándékot.
▸
Extract Class / Interface
Felelősség kiemelése új osztályba (SRP), vagy közös interfész definiálása.
▸
Replace Magic Number with Constant
Literális értékek elnevezett konstansokkal való felváltása.
⚠
Feltétel: tesztek előtte!
Refaktorálás előtt legyen teszt lefedettség — különben nem tudod, hogy eltörted-e a kódot.

🗄️
Adatbázis-tervezés & SQL Elmélet
1 — Adatbázis-tervezés lépései & normalizálás
📐Tervezési lépések
1. Követelmény-elemzés
Milyen adatokat kell tárolni? Milyen lekérdezések kellenek? Az üzleti igények feltérképezése.
2. Fogalmi modell (ER-diagram)
Entitások, attribútumok és kapcsolatok azonosítása. Eszköz: Chen-jelölés vagy crow's foot. Adatbázis-független.
3. Logikai modell
ER-diagram leképezése relációs modellre: táblák, elsődleges kulcsok (PK), idegen kulcsok (FK) definiálása.
4. Normalizálás
A redundancia és anomáliák megszüntetése normálformák alkalmazásával (1NF → 2NF → 3NF).
5. Fizikai modell
Adatbázis-specifikus implementáció: adattípusok, indexek, tárolt eljárások, partícionálás.
🔢Normálformák (Normalizálás)
1NF
Első normálforma
Minden cella atomi értéket tartalmaz (nincs lista/halmaz egy cellában). Minden sornak van egyedi azonosítója (PK).
❌ Rossz: telefon = "06-20-111, 06-30-222"
2NF
Második normálforma
1NF + minden nem-kulcs attribútum teljes funkcionális függésben legyen a teljes elsődleges kulcstól (összetett PK esetén releváns).
❌ Rossz: összetett PK (rendelés_id, termék_id) + termék_neve (csak termék_id-tól függ)
3NF
Harmadik normálforma
2NF + nincs tranzitív függés: nem-kulcs attribútum ne függjön másik nem-kulcs attribútumtól.
❌ Rossz: irányítószám → város (mindkettő nem-kulcs, de összefügg)
BCNF
Boyce-Codd normálforma
3NF szigorítása: minden funkcionális függés bal oldala szuperkulcs legyen. Ritka esetekben szükséges.
🔑Kulcsok & kapcsolatok
PK
Elsődleges kulcs (Primary Key)
Egyértelműen azonosít egy sort. Nem lehet NULL, egyedi. Általában AUTO_INCREMENT egész szám vagy UUID.
FK
Idegen kulcs (Foreign Key)
Hivatkozás egy másik tábla PK-jára. Referenciális integritást biztosít. ON DELETE CASCADE / SET NULL
UK
Egyedi kulcs (Unique Key)
Egyediséget garantál, de lehet NULL (egy-egy NULL megengedett). Pl. felhasználónév, email.
1:1
Egy-az-egyhez kapcsolat
Ritka. Pl. Felhasználó ↔ FelhasználóProfil. Az FK általában az egyik táblában egyedi kulcsként szerepel.
1:N
Egy-a-többhöz kapcsolat
Leggyakoribb. Pl. Kategória → Termékek. Az FK a „több" oldali táblában van.
N:M
Több-a-többhöz kapcsolat
Kapcsolótáblán keresztül. Pl. Diák ↔ Tantárgy → diák_tantárgy(diák_id, tantárgy_id). Mindkét FK együtt alkotja a PK-t.
2 — SQL lekérdezések & haladó technikák
🔍JOIN típusok — szemléletes összehasonlítás
INNER JOIN
Csak a mindkét táblában meglévő párok. A metszet.
LEFT JOIN
Bal tábla összes sora + jobb tábla egyező sorai (NULL ha nincs pár).
RIGHT JOIN
Jobb tábla összes sora + bal tábla egyező sorai (NULL ha nincs pár).
CROSS JOIN
Descartes-szorzat: bal × jobb. A és B tábla minden kombinációja.
MySQL — JOIN példák
-- INNER JOIN: csak a kategóriás termékek
SELECT t.nev, k.nev AS kategoria
FROM termekek t
INNER JOIN kategoriak k ON t.kategoria_id = k.id;

-- LEFT JOIN: összes kategória, akár nincs terméke
SELECT k.nev, COUNT(t.id) AS termek_db
FROM kategoriak k
LEFT JOIN termekek t ON t.kategoria_id = k.id
GROUP BY k.id, k.nev;

-- Önhivatkozó JOIN: főnök-beosztott kapcsolat

📊Aggregáció & csoportosítás
MySQL — GROUP BY, HAVING, aggregátok
-- Aggregáló függvények
SELECT
  kategoria_id,
  COUNT(*) AS darab,
  AVG(ar)   AS atlag_ar,
  MAX(ar)   AS legdragabb,
  MIN(ar)   AS legolcsobb,
  SUM(ar)   AS osszeg
FROM termekek
WHERE aktiv = 1           -- sorok szűrése (GROUP BY ELŐTT)
GROUP BY kategoria_id
HAVING COUNT(*) > 5       -- csoportok szűrése (GROUP BY UTÁN)
ORDER BY atlag_ar DESC
LIMIT 10;
WHERE vs HAVING: WHERE aggregáció előtt szűr (sorokra), HAVING aggregáció után szűr (csoportokra). A kettőt kombinálni is lehet.

-- DCL: jogosultságok

🚀Indexek & teljesítmény
IDX
Mi az index?
A könyv tárgymutatójához hasonló — a DB nem végigolvassa a táblát, hanem az indexen keres. Gyorsítja a SELECT-et, lassítja az INSERT/UPDATE-et.
B+
B-Tree index (alapértelmezett)
Rendezett fa struktúra. Jó: egyenlőség, tartomány (BETWEEN, <, >), rendezés. MySQL InnoDB alapértelmezetten ezt használja.
HASH
Hash index
Csak egyenlőség vizsgálatra jó (=). Rendezésre és tartományra nem. MEMORY engine használja.
MySQL — EXPLAIN elemzés
-- Lekérdezési terv megjelenítése
EXPLAIN SELECT * FROM termekek WHERE nev = 'Laptop';
-- type=ALL → teljes tábla scan (lassú, nincs index)
-- type=ref → index használva (gyors)

-- Összetett (composite) index
CREATE INDEX idx_kat_ar ON termekek(kategoria_id, ar);
-- Bal-elöl szabály: (kategoria_id) és (kategoria_id, ar) lekérdezéseket gyorsít
-- De (ar) egyedül NEM használja ezt az indexet!

JS — var vs let vs const, típusellenőrzés
// var — function scope, hoisting, kerülendő!
var x = 10;   // elérhető a function tetején (hoisting)

// let — block scope, újraértékelhető
let szamlalo = 0;
szamlalo = 1;  // OK

// const — block scope, nem újraértékelhető
const PI = 3.14;  // primitívnél valóban konstans
const tomb = [1, 2];
tomb.push(3);     // OK! a referencia konstans, nem a tartalom

// Típusellenőrzés
typeof "hello"   // "string"
typeof 42        // "number"
typeof null      // "object" ← historikus bug!
typeof []        // "object" ← tömb is object
Array.isArray([]) // true ← tömb ellenőrzés

// Típuskényszer (type coercion)
"5" + 3   // "53" (string összefűzés!)
"5" - 3   // 2   (szám kivonás)
"5" == 5  // true  (laza egyenlőség, kerülendő!)
"5" === 5 // false (szigorú egyenlőség, MINDIG ezt!)

async function felhasználóLekér(id) {

const arr = [1, 2, 3, 4, 5];

arr.filter(x => x > 2)        // [3,4,5]       — szűrés feltétel alapján

arr.findIndex(x => x > 3)      // 3             — első megfelelő index

arr.every(x => x > 0)          // true          — minden ilyen?
arr.includes(3)               // true          — tartalmazza?
arr.flat(2)                    // lapít 2 mélységig
arr.flatMap(x => [x, x*2])     // map + flat egyszerre
arr.slice(1, 3)               // [2,3]         — kivágás (nem módosít)
arr.splice(1, 2, 99)          // módosít: [1,99,4,5] ← romboló!

Weboldal, amely mobilalkalmazásként is működik. Service Worker cache, offline mód, telepíthető. Manifest.json definiálja az app metaadatait.

CMS típusok, WordPress alapok, beépülők
📝CMS típusok
A CMS (Content Management System) lehetővé teszi webes tartalmak kezelését programozói tudás nélkül.
Hagyo
Hagyományos / Coupled CMS
Frontend és backend egyben. WordPress, Joomla, Drupal. A tartalom és a megjelenítés szorosan összekapcsolt — témák/sablonok szabják meg a designt.
Head
Headless CMS
Csak a tartalom kezelése, frontend nélkül — API-n (REST/GraphQL) adja ki az adatokat. Pl. Contentful, Strapi, Sanity. Bármilyen frontend framework-kel használható.
Statik
Statikus oldalgenerátor
Build időben generálja a HTML oldalakat. Hugo, Jekyll, Eleventy. Gyors, biztonságos, de dinamikus tartalom korlátozott.
SaaS
SaaS / Hosted CMS
Wix, Squarespace, Webflow. Nem kell hosztingot kezelni, drag-and-drop szerkesztő. Korlátozott testreszabhatóság.
🔷WordPress architektúra
A világ weboldalainak ~43%-a WordPress-en fut. PHP + MySQL alapon, Apache/Nginx szerverrel.
Téma
Témák (Themes)
A megjelenést szabályozzák. Kötelező fájlok: style.css, index.php. Hierarchia: single.php → index.php. Child theme: szülő téma felülírása módosítás nélkül.
Plugin
Beépülők (Plugins)
Funkcióbővítés aktiválható/deaktiválható modulokkal. Pl. WooCommerce (webáruház), Yoast SEO, Elementor, Contact Form 7.
Hook
Hook rendszer
Action: esemény bekövetkezésekor fut le (add_action()). Filter: adatot módosít visszatérés előtt (add_filter()). A WP plugin API alapja.
DB
WordPress adatbázis struktúra
Főbb táblák: wp_posts, wp_postmeta, wp_users, wp_options, wp_terms. A wp_options key-value párokban tárolja a beállításokat.
🔒CMS biztonság & teljesítmény
Bizton
Biztonsági alapok
Rendszeres frissítések (WP core, témák, pluginok). Erős jelszavak, kétfaktoros azonosítás. Admin URL megváltoztatása. Fájljogosultságok: wp-config.php → 600.
Cache
Teljesítmény és cache
Page cache: WP Super Cache, W3 Total Cache. CDN: Cloudflare. Képoptimalizáció (WebP), lazy loading, adatbázis optimalizáció.
REST
WordPress REST API
Beépített API: /wp-json/wp/v2/posts. Headless WordPress megvalósítható vele — bármilyen JS frontend csatlakoztatható.
SEO
SEO alapfogalmak
